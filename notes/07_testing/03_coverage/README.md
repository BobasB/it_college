# Покриття коду
> Покриття показує, які рядки та розгалуження програми були виконані тестами. Воно допомагає знайти неперевірений код, але саме по собі не доводить якість тестів.

## Встановлення
```bash
pip install coverage pytest pytest-cov
# або
poetry add --group dev coverage pytest pytest-cov
```

## Приклад
1. Перейдіть до `example/testing/03_coverage`.
2. Запустіть тести:
    ```bash
    poetry run pytest -v
    ```
3. У прикладі є і pytest-тести у `test_app.py`, і unittest-тести у `test_unittest.py`. Запускайте їх окремо, щоб бачити, який набір сформував звіт:
    ```bash
    poetry run coverage erase
    poetry run coverage run -m unittest discover
    poetry run coverage report -m

    poetry run coverage erase
    poetry run coverage run -m pytest
    poetry run coverage report -m
    ```
4. Або використайте плагін `pytest-cov`:
    ```bash
    poetry run pytest --cov=app --cov-branch --cov-report=term-missing -v
    ```

## Як читати звіт
У таблиці `coverage report -m` зверніть увагу на такі стовпці:
- `Stmts` — кількість виконуваних операторів у файлі;
- `Miss` — скільки операторів не виконано;
- `Branch` — кількість можливих переходів між гілками умов;
- `BrPart` — частина переходів, для яких виконано не всі можливі гілки;
- `Missing` — номери рядків, які варто перевірити.

Line coverage показує, чи виконувався рядок хоча б раз. Branch coverage показує, чи пройшли тести кожен напрямок умовного переходу. Відсоток не гарантує, що тести перевіряють правильні результати.

## Цикл збору даних
`coverage run` запускає тести та записує дані у файл `.coverage`; `coverage report` читає ці дані й формує звіт. Щоб не змішувати результати різних запусків, спочатку очищайте попередній файл:
```bash
poetry run coverage erase
poetry run coverage run -m pytest
poetry run coverage report -m
```

Якщо запустити `coverage report` до `coverage run`, актуальних даних може не бути. Якщо спершу виконати тести, а потім інший набір, результати можуть додатися до того самого файлу, тому для порівняння наборів використовуйте `coverage erase` перед кожним вимірюванням.

## Розгалуження
1. У `app.py` властивість `get_angles` має кілька гілок для різних типів фігур.
2. Якщо протестувати лише трикутник, частина умов залишиться непокритою.
3. :star: Додайте тести для квадрата, прямокутника і трикутника.
4. :star: Перезапустіть `coverage report -m` і поясніть, які рядки були пропущені до змін.

## HTML-звіт і налаштування
1. Створіть HTML-звіт:
    ```bash
    poetry run coverage html
    ```
2. Відкрийте `htmlcov/index.html` у браузері та дослідіть підсвічені рядки.
3. Файл `.coveragerc` потрібен для збереження налаштувань `coverage.py` у самому проєкті. Завдяки йому не потрібно щоразу передавати однакові параметри в командному рядку.
   - секція `[run]` визначає, який код аналізувати та чи враховувати розгалуження;
   - `source = .` означає аналіз Python-файлів у поточній папці прикладу;
   - `branch = true` вмикає перевірку переходів між гілками `if` та іншими умовами;
   - секція `[report]` визначає файли, які не потрібно включати до звіту, наприклад самі тести та службові файли.

   Приклад `.coveragerc`:
    ```ini
    [run]
    source = .
    branch = true

    [report]
    omit =
        test_*.py
        */tests/*
        */__init__.py
        */.venv/*
    ```
4. У `pyproject.toml` можна додати секцію `[tool.coverage]`, щоб зберегти налаштування у файлі конфігурації проєкту. Це дозволяє запускати `coverage` без додаткових параметрів командного рядка.
    Приклад `pyproject.toml`:
    ```toml
    [tool.coverage.run]
    source = ["src"]
    branch = true

    [tool.coverage.html]
    directory = "htmlcov"

    [tool.coverage.report]
    skip_empty = true
    omit = [
        "*/tests/*",
        "test_*.py",
        "*/.venv/*"
    ]
    exclude_lines = [
        'if __name__ == "__main__":',
        'def lambda_handler',
    ]
    fail_under = 80
    ```

5. :star: Додайте у звіт консольний або HTML-результат, відсоток покриття та перелік непокритих рядків.
6. :fire: Встановіть власний мінімальний поріг покриття, доповніть тести й перевірте його командою:
    ```bash
    poetry run pytest --cov=app --cov-branch --cov-fail-under=90
    ```

## Межі вимірювання та виключення
Параметр `source` задає код, який потрібно вимірювати. Для навчального прикладу `source = .` означає поточну папку; у більшому проєкті вкажіть каталог пакета, наприклад `src/my_app`. Тести та середовища зазвичай виключають зі звіту параметрами `omit`, але саму програму виключати не потрібно.

Іноді рядок справді неможливо або недоцільно виконати в тестовому середовищі. Тоді його можна позначити:
```python
if __name__ == "__main__":  # pragma: no cover
    main()
```

Використовуйте `pragma: no cover` лише для коду, який свідомо не є частиною тестованої поведінки. Не додавайте це позначення, щоб штучно підвищити відсоток.

### Завдання
- :star: Перевірте, що `source` охоплює `app.py`, а тестові файли не з'являються у звіті.
- :star: Позначте точку входу скрипта через `pragma: no cover` та порівняйте результати.
- :fire: Знайдіть коректний приклад виключення рядка й обґрунтуйте, чому він не змінює покриття важливої логіки.

## Звіти для людей та інструментів
HTML-звіт зручний для перегляду рядків у браузері:
```bash
poetry run coverage html
```

XML-звіт можна передавати CI-системам та сервісам аналізу покриття:
```bash
poetry run coverage xml
```

У GitHub Actions можна запустити тести, згенерувати `coverage.xml` і завантажити його як артефакт або передати сервісу покриття. Це продовжує тему автоматизації з [роботи №08](../../08_github_actions/README.md). Після виконання CI порівняйте локальний і CI-звіти.

### Завдання
- :star: Згенеруйте HTML та XML-звіти й поясніть, для кого призначений кожен формат.
- :fire: Додайте перевірку coverage у CI та налаштуйте невдалий статус, якщо поріг покриття не досягнуто.

## Чого coverage не доводить
Можна виконати рядок коду, але не перевірити результат. Наприклад, тест, який лише викликає функцію без `assert`, може збільшити відсоток покриття, не виявивши неправильне значення.

### Завдання
- Напишіть тест, який викликає `get_angles`, але не перевіряє результат. Зафіксуйте coverage.
- Додайте перевірку очікуваного значення та порівняйте, що саме тепер гарантує тест.
- Поясніть, чому 100% line coverage не означає відсутності помилок.

### Що не потрібно комітити
Додайте до `.gitignore` службові файли `__pycache__/`, `.coverage`, `htmlcov/` і `.pytest_cache/`. Саме HTML-представлення можна додати до звіту, але не до навчального репозиторію.

### Звіт
- покажіть команду запуску тестів;
- порівняйте покриття до і після додавання тестів;
- поясніть різницю між покриттям рядків і покриттям розгалужень.
- додайте результати окремих запусків `unittest` і `pytest`;
- поясніть, чому використали або не використали `pragma: no cover`;
- додайте HTML- або XML-звіт та поясніть його призначення.
